RELATIONSHIPS FILE RULES

FILE FORMAT

- UTF-8 CSV.
  Save from Excel as 'CSV UTF-8'. Other encodings fail the whole run. Standard CSV quoting (RFC 4180).

- First row is the header.
  Spreadsheet row numbers are used in Issues, with the header as row 1.

- All seven columns are required in the header.
  Provider Unique ID, Individual NPI, Facility Unique ID, Facility NPI, Facility Shipping Address, Relationship Start Date, Terminate. A missing column fails the whole run. Values may be blank. Column names must match exactly, including case and spacing.

- The relationship field columns are optional.
  Limitations, Practitioner Scheduling URL and Telemedicine Capability may be left out of the header (see RELATIONSHIP FIELDS). A misspelt one is ignored without a warning. "Include in Directory?" is not used: that field is calculated by Salesforce.

- Every row has the same number of columns as the header.
  A row with a different count is a row error (COLUMN_COUNT) and is skipped.

LIMITS

- At most 5,000 data rows and 3 MB.
  Larger files fail the run before any row is processed.

BEFORE YOU START

- Providers must already exist.
  This file never creates Providers or facilities. Ingest the personnel file first; rows for unknown Providers fail with UNKNOWN_PROVIDER and can be re-run later.

ORGANIZATION SCOPE

- A roster only changes relationships at its own Organization's facilities.
  The scope is the roster's Organization and every Organization below it (sub-organizations, their sub-organizations, and so on), never its parents. A facility is in scope when its Healthcare Facility's Legal Owner is one of these. A facility with no Legal Owner is in no roster's scope.

MATCHING

- The Provider is found by Provider Unique ID, or by Individual NPI.
  Same rules as the personnel file, except that no match is an error (UNKNOWN_PROVIDER).

- The facility is found by Facility Unique ID, then Facility NPI, then address.
  Only the first key given decides; the others must agree with it. NPI and address only search facilities in the roster's scope and must find exactly one. Not needed when Terminate = All.

ACTIVE RELATIONSHIP

- A relationship is active, for intake, when it has not ended: its Termination Date is blank or after the run date.
  Decided 2026-11-06. Only active relationships are terminated or count as already existing. The start date and the Active checkbox (IsActive) do not matter: a relationship that starts in the future is active for intake, and one whose Termination Date is the run date has ended. This follows the org's Active__c formula (started, and not past its Termination Date) except in those two cases.

- Intake never reads or changes the Active checkbox (IsActive).
  Decided 2026-11-06.

ACTIONS

- Terminate blank: create.
  No active relationship: one is created, with the start date (the run date if blank) and the relationship fields if given - Inserted. Already active: relationship fields that differ are updated - Updated; otherwise nothing changes - Unchanged. The start date is never changed. A Provider who left and returns gets a new relationship; the old one is kept as it is.

- Terminate = Single: end one relationship.
  The active relationship's Termination Date is set to the file's Termination Date, or the run date if blank, and its Termination Notes to the file's if given - Terminated (Unchanged if it already had both). A relationship whose Termination Date is the run date or earlier has ended for intake (by the Active__c formula it stays active through that date); one dated later stays active until then. None active: nothing changes, warning NO_ACTIVE_RELATIONSHIP - Unchanged.

- Terminate = All: end all of the Provider's relationships in scope.
  Every active relationship of the Provider at a facility in the roster's scope is terminated, with the same date and notes - Terminated. Relationships at other Organizations' facilities are not touched. None active: warning NO_ACTIVE_RELATIONSHIP - Unchanged.

- Termination Date and Termination Notes (optional columns) are used by terminate rows only.
  Termination Date: MM/DD/YYYY, past or future; blank means the run date. A malformed one is a row error (INVALID_TERMINATION_DATE). Termination Notes: overwrite the stored notes; blank leaves them; longer than 255 characters is ignored with warning INVALID_VALUE (the termination still happens). No termination reason is set.

- A create row (Terminate blank) with a Termination Date or Termination Notes is an error.
  TERMINATION_COLUMNS_ON_CREATE_ROW; nothing is created.

- A relationship cannot end before it starts.
  A termination dated before a relationship's start date is a row error (TERMINATION_BEFORE_START); ending on the start date is allowed. With Terminate = All, nothing is terminated if any of the relationships would end before it starts.

- Terminating again replaces a scheduled end.
  A relationship with a future Termination Date is still active; a terminate row replaces its date (and notes, if given).

RELATIONSHIP FIELDS

- Limitations, Practitioner Scheduling URL and Telemedicine Capability set fields of the relationship.
  On a create row they are written to a new relationship, and to an active one where they differ (compared exactly, case and spaces included). A blank cell never changes or clears anything. Telemedicine Capability is Yes or No (any case). The Scheduling URL is not checked as a URL. An invalid or over-long value is ignored with warning INVALID_VALUE; the rest of the row is still ingested.

- Terminate rows ignore them.
  A termination never changes these fields; if any is filled in, the row gets one warning, RELATIONSHIP_COLUMNS_IGNORED, naming the columns.

ROWS IN THE SAME FILE

- Rows are applied in file order and never create duplicates.
  Two create rows for the same Provider and facility create one relationship (the second is Unchanged). A create followed by a terminate ends with the relationship terminated.

DATA ANOMALIES

- Several active relationships for one Provider and facility.
  Should not exist. A terminate ends all of them and a create creates nothing; either way the row gets warning MULTIPLE_ACTIVE_RELATIONSHIPS so the data can be investigated.

OUTCOMES

- Every row ends as Inserted, Updated, Terminated, Unchanged or Error.
  Counts are rows, not relationships: a Terminate = All row that ends three relationships counts once. Errors and warnings are recorded as Issues on the Run, with row number, code, message, Provider and facility.

SIDE EFFECTS

- Intake no longer triggers the org's payer participation flows.
  Those flows react to the Active checkbox (IsActive), which intake does not set, so creating or terminating a relationship through intake neither creates nor ends a Provider Plan Participation. Updating relationship fields on an existing relationship is a save, so the flows run then, as they would for any edit.

RUNS

- One run per roster at a time, across both files.
  A personnel run and a relationships run of the same roster cannot overlap; different rosters can. A run processes the file version that was current when it started.

- Re-running a file is safe.
  Relationships already created come out Unchanged; terminations already done come out Unchanged, with a warning when the relationship has already ended (a future-dated one with the same date and notes has nothing to change).

PRIVACY

- Messages name Providers, facilities and Organizations.
  They never contain sensitive Provider values.

ACCESS

- Who can run it.
  Users who can edit the roster can start and cancel runs. Seeing Runs and Issues needs the Roster_Ingestion_Files permission set. Records are matched and written regardless of the user's own access to them.
